# kharon — spec (draft)

Status: draft, 2026-10-30. Repo: `CycleFive/kharon`. Name decided: kharon. Language: Rust.

kharon is a broker that runs on owner-controlled hardware, in front of a Bitwarden account it does not own: the owner's Bitwarden cloud Password Manager, or a self-hosted Vaultwarden. It decrypts a dedicated Bitwarden collection client-side and fills credentials into a browser tab over CDP. Agents get metadata and fill status. They never get plaintext.

Requirement IDs are `REQ-<AREA>-NNN`. Each has one testable acceptance criterion (AC). Areas: GOAL, CRY, EXP, ARCH, API, APR, ORG, AUD, RL, REV, MEM, DEP.

## 1. Goals and non-goals

Goals
- G1. A fill never puts a secret (password, TOTP seed, TOTP code, card number, custom hidden field) into agent context, MCP/HTTP responses, logs, the agent host's disk, or any process running as the agent's OS user other than the browser renderer that owns the target field.
- G2. Every fill is bound to an item, an origin, an agent identity, and a grant. Every fill is audited.
- G3. Blast radius is one Bitwarden collection, not the owner's vault.
- G4. Works against Vaultwarden and official Bitwarden (cloud or self-hosted) using only the public client API.

Non-goals
- N1. Protecting a secret after it lands in a DOM field from code running in that page or from an actor holding full CDP/JS on that tab (§2.4).
- N2. Running inside Vaultwarden or patching its server code.
- N3. Writing to the vault: creating, editing, or rotating items. v1 is read-only.
- N4. Passkeys/WebAuthn assertions, SSH keys, and card or identity autofill in v1 (OQ-6).
- N5. Multi-owner or multi-tenant operation.

| ID | Requirement | AC |
|---|---|---|
| REQ-GOAL-001 | No API surface returns secret-bearing fields. | A schema test enumerates every MCP tool and HTTP route response type. None contains a type marked `Secret<…>`. A fuzzed fill run with canary secrets finds 0 canary bytes in responses, broker logs, and audit log. |
| REQ-GOAL-002 | Canary secrets never reach the agent host filesystem. | E2E: fill a 32-byte random canary. `grep -r` across the agent host's `/` (excluding `/proc`) and the browser profile dir after the fill finds 0 hits. Chromium password saving is disabled. |

## 2. Threat model

### 2.1 Actors

| Actor | Trust | Capabilities assumed |
|---|---|---|
| Agent (LLM + tool harness) | Untrusted: curious or compromised, including via prompt injection | Calls kharon API with its token. Drives the browser: navigates, clicks, reads DOM and screenshots, and may run JS in pages. Reads anything its OS user can. |
| Dashboard (an MCP client connected with OAuth, §4.1) | Untrusted, like the agent. Allow-listed by the operator (REQ-OAU-002). | Holds the access and refresh tokens of its own Connect only. Can call the tools its scopes allow, and so request grants and ask for fills, never approve them (REQ-OAU-006). |
| Agent host (Linux box with Chromium) | Partially trusted. Assume the agent's OS user is compromised. Root is not compromised, otherwise G1 is lost (§2.4). | Runs Chromium and the CDP tunnel endpoint. |
| Network (LAN/WAN between hosts) | Untrusted | Passive and active MitM. |
| Internet stranger (via the public edge) | Untrusted | Can reach only what `[public_ingress]` serves (`POST /mcp`, `GET /connector`). Holds no token. Bounded by the transport budgets (REQ-RL-005) and the cost of Argon2id; refusals at that layer are unaudited, so probing cannot grow the audit log. |
| Internet stranger (via the owner hostname, public mode) | Untrusted | Holds no session. With Access off, can load the sign-in and enrollment pages and call the unauthenticated owner routes; with `[owner_ui.access]` on and no Access token, reaches only the exempt routes, which include the ntfy redeem routes (`/owner/approve/<token>`, `/owner/deny/<token>`; the single-use token in the URL is the credential, REQ-APR-004). Each source is bounded by the throttle, and the itemized audit entries by the ceiling (§2.4, REQ-APR-009). The throttle applies to a source the edge names with `CF-Connecting-IP`; a request without a usable header is audited with its TCP peer and not throttled, which rests on the edge always sending the header. A valid Access token is not a session: the passkey is still required. |
| Vaultwarden server | Honest-but-curious about ciphertext (Bitwarden's model). May serve stale or malicious ciphertext or org keys. | Sees ciphertext, the master-password hash, and API key use. Never sees plaintext. |
| Broker host (owner hardware) | Trusted | Holds decrypted keys in RAM. |
| Operator (managed deploy) | Trusted exactly as the broker host is | Has root on the box, the owner socket, the config and the edge dashboard. Can mint an enrollment code (short-lived and single-use, printed on their terminal; whoever holds it for its 120 s can register a passkey), approve, deny and panic over the CLI, change the config, and read process memory after an unlock. The passkey and Access do not constrain them. The master password is never stored. It stays the customer's only if the customer ran `kharon init` themselves (it prints the password on the terminal that runs it). Even then the Operator can capture it at any unlock: on the web by altering the page at the edge (§2.4), on the CLI from the terminal it is typed into. Approve, deny and revoke over the CLI are audited as channel `cli`. Minting an enrollment code, storing a passkey, listing passkeys and removing one are audited (`passkey_enroll_code`, `passkey_enrolled`, `passkey_listed`, `passkey_removed`; #249, #258). Storing a passkey is channel `web_ui`, so an Operator-enrolled passkey acts as `web_ui`, like the owner. Listing and removing from the CLI are channel `cli`; from the signed-in page, `web_ui`. As root the Operator can rewrite the local audit log; that shows only against the off-host checkpoints (REQ-AUD-002), and only if the customer holds that stream. |
| Owner | Trusted | Unlocks and approves. Holds the master password of the kharon Bitwarden account. |
| Web origin being filled | Untrusted for everything except receiving its own credential | Can redirect, iframe, and race navigations. |

### 2.2 Assets

A1: plaintext secrets of items in the kharon collection. A2: kharon account master password, master key, user key, RSA private key, org key(s). A3: agent tokens, OAuth access and refresh tokens (§4.1) and grants. A4: audit log integrity. A5: the owner's other vault items. kharon never holds keys to these, by construction.

### 2.3 Trust boundaries

B1 agent ↔ broker API: authN with an agent token or an OAuth access token (§4.1), authZ with grants (and, for OAuth tokens, scopes). B2 broker ↔ Chromium: authenticated encrypted tunnel (WireGuard/mTLS or agent-initiated TLS reverse), CDP. B3 broker ↔ Vaultwarden: TLS, Bitwarden API. B4 owner ↔ broker: approval channel with owner authN, by three paths: the owner socket (peer uid); the web UI (a passkey; in public mode it sits behind the edge by placement, as B6); and the ntfy one-time action (REQ-APR-004), whose single-use URL token is the credential, travels in the ntfy message for 120 s, and is exempt from the `Origin` rule and from Access. B5 renderer page ↔ field value: not enforceable by kharon. B6 edge ↔ broker `[public_ingress]` and, in public mode, the owner UI listener: placement, not cryptography. `CF-Connecting-IP` names the client **for throttling and audit only** — it never gates auth or any decision beside it (REQ-API-010, #206) — and only when the connection peer is loopback or, on `[public_ingress]`, listed in `trusted_proxies`. Any other peer is the client address itself, so a reachable non-loopback listener cannot be talked into another throttle key or audit `client_ip`. The owner UI binds loopback, so every peer it can accept is the edge. On `[api]` the header is ignored and the connection peer is the client.

### 2.4 Protects / does not protect

| Protects against | Mechanism |
|---|---|
| Secret in LLM context, tool output, shell history, agent logs | No read endpoint. Fill returns status only. (REQ-API-*) |
| Agent filling credential X on attacker origin Y (phishing or prompt injection) | eTLD+1/host binding checked atomically in the live frame (REQ-ORG-*) |
| Unapproved or excessive use | Grants, TTL, rate limits (REQ-APR-*, REQ-RL-*) |
| Unauthenticated flood against the public `/mcp` (Argon2id exhaustion, cheap-read abuse) | Transport budgets counted before auth, body and JSON-depth caps (REQ-API-010, REQ-RL-005) |
| A non-loopback peer of `[public_ingress]` choosing its throttle key or audit `client_ip` with `CF-Connecting-IP` | The header is honoured only from a loopback peer or `trusted_proxies` (REQ-API-010) |
| Silent misuse / after-the-fact denial | Hash-chained audit with signed checkpoints (REQ-AUD-*) |
| Theft of agent host disk | Nothing secret is persisted there |
| Vaultwarden DB compromise | Standard Bitwarden E2EE. kharon adds no server-side plaintext. |
| A stolen dashboard access or refresh token | Access tokens live 1 h and are bound to `/mcp`. Refresh tokens rotate, and a retired one presented again ends the Connect. Disconnect is immediate. A token can only request (REQ-OAU-004/-005/-006). |
| Consent phishing: a lookalike site asking the owner to Connect | Only operator-allow-listed clients can show a consent screen. The screen names the client and its hostnames (REQ-OAU-002/-003). |
| Broker restart or crash dump leaking keys | mlock, no core dumps, starts locked (REQ-MEM-*) |
| A stranger evicting or blocking the owner's sign-in on the published owner UI | Sign-in and enrollment ceremonies are sealed tokens, not a table, so no number of unauthenticated requests can evict another client's (REQ-APR-009) |
| A cross-site page locking the owner out | A wrong `Origin` never counts toward the throttle or the per-session failure cap, so it cannot sign the owner out (REQ-APR-009) |
| A stolen owner-UI session guessing from many addresses | 10 `owner_auth_fail` entries attributed to that session end it: any route, any source, any detail except a refused `Origin`. The next request with the cookie is `401`. One `owner_auth_fail` with `detail_code` `session_ended` records it. The owner signs in again with the passkey (REQ-APR-009, #254). |
| A hostname mis-pointed at the owner listener | Every request's `Host` must name the public host, else `421` (REQ-APR-009) |
| A stranger filling the audit log through failed owner-UI attempts | At most 20 itemized `owner_auth_fail` entries a minute plus 5 `throttled` entries (and the count of the rest) (REQ-APR-009) |
| A stolen or lost owner passkey | `kharon passkey remove`, or the owner page when it is not the last passkey, drops that credential and every session opened with it. An assertion from it is refused. Other passkeys keep working (REQ-APR-005, REQ-APR-006, #258). |

| Does NOT protect against | Why |
|---|---|
| Agent reading the field after fill (`input.value`, `Runtime.evaluate`, DOM snapshot, page JS) when the agent has JS/CDP on the same tab | The plaintext must exist in the renderer for the form to submit. 1Password's agent fill has the same property. Mitigations, which reduce exposure but do not remove it: `fill_and_submit`, clear-on-failure, password-type fields only, and an optional agent tool profile with no `evaluate` (OQ-3). |
| Root on agent host | Can read Chromium memory and tunnel keys |
| Malicious or XSS'd page on a correctly bound origin | Page receives its own credential by design |
| Owner approving a bad request | The human is the oracle. kharon shows origin, item, and agent in the prompt. |
| A TLS-terminating edge (Cloudflare) reading OAuth codes and tokens | Accepted on a managed deploy: the edge already sees the `/mcp` bearer token. The limits are short access tokens, refresh reuse detection and Disconnect, and CDP stays inside the connector's pinned inner TLS (#199). |
| A local process on a host-networked broker host spoofing `CF-Connecting-IP` | On a host-networked deploy every local process shares the loopback the edge uses, so the header is forgeable there (in compose the netns holder narrows this to the edge). Accepted because the address can only move a request between throttle buckets and change an audit field — never an auth outcome (REQ-API-010, #206). Single-purpose hosts only (REQ-DEP-006). |
| Someone sharing the owner's address throttling it | A source with 10 failures in 10 minutes is refused until ten minutes after its first counted failure (a fixed window), and a neighbour behind the same address (or IPv6 /64) can cause them. The CLI is the way back (REQ-APR-009). |
| An edge that stops sending `CF-Connecting-IP` | The per-source throttle is off for sign-in, enroll and unlock; visible as a rising `owner_ui_without_edge_address` in the owner socket's status (REQ-APR-009) |
| A stolen session cookie's first guesses at the master password | The session ends after 10 failures, so those 10 still run. What makes them useless is the password's strength (≥ 128 bits, REQ-DEP-007) (REQ-APR-009, #254). |
| The edge (or an Operator holding it) using the owner's session and capturing the master password on a web unlock | Accepted on a managed deploy, like the OAuth row above. The edge sees the session cookie and can replay it for the session's 15 minutes to approve, deny, revoke, panic and begin an unlock; it also serves the page's JavaScript and the unlock key. A web unlock encrypts the password in the page (ECDH, AES-GCM) so it stays out of HTTP bodies, logs and buffers, but the page and the key both come through the edge, which can alter either to capture it. Unlocking over the CLI on the box keeps the password off the edge, but only for whoever has a shell there; on a managed deploy that is the Operator, so a managed customer has no way to unlock without trusting the edge or the Operator. The cookie is `__Host-`, `Secure`, `HttpOnly`, `SameSite=Strict`, which protects against browsers, not the edge (REQ-APR-009). |
| Phishing of the web unlock | The unlock form takes the master password in a page. A lookalike hostname can copy that page. The passkey is origin-bound, so it protects sign-in but not a password typed into a copied unlock form. |
| A reader of the ntfy topic approving a request | In public mode the approve and deny action URLs are on the public owner hostname and exempt from `Origin` and Access, and the single-use token in the URL is the credential. Whoever can read the ntfy message (the ntfy server's operator, any subscriber to an open topic) can approve a pending request as a `once` grant for its item, or deny it, within 120 s, from anywhere. This rests on the topic's confidentiality: a private topic with auth (`token_file`), on a server the customer trusts (REQ-APR-004). |
| A flood from many sources on the owner hostname | Out of scope beyond the named bounds; Cloudflare sits in front. A flood can use up the itemized audit entries, so that a real failure in the same minute is only counted. |
| Compromised broker host | Holds keys |
| Malicious Vaultwarden swapping ciphertext under the org key | Undetected item substitution within the collection is possible because Bitwarden cipher fields are not bound to the item ID. The URI binding uses the decrypted item URIs, so a swapped item still fails the origin check unless the attacker controls both. See OQ-7. |

## 3. Architecture

```
 owner hw                                     agent host
┌──────────────────────────┐  WG / mTLS /       ┌─────────────────────────┐
│ vaultwarden  ◄─TLS─ kharond │  agent-connector  │ chromium (user: browser) │
│                 │  ▲  ▲   ├──── CDP (ws) ─────►│   ▲ CDP (agent session)  │
│                 │  │  └─ approvals (ntfy/web/CLI)  │ agent (user: agent)     │
│                 │  └── MCP/HTTP (agent token) ◄──┤  (path B: agent dials)  │
└──────────────────────────┘                    └─────────────────────────┘

Two transport classes for B2 (REQ-ARCH-002):
  (A) WireGuard/mTLS — broker dials agent host (capable hosts).
  (B) agent-connector — agent holds outbound TLS; broker CDP rides the reverse
      path (egress-shaped hosts: outbound TCP/TLS only, no UDP / CAP_NET_ADMIN).
      The pinned TLS runs directly to the broker, or inside a WebSocket at
      /connector on the public hostname (#199).
```

### 3.1 Bitwarden account and crypto model

kharon logs in as a dedicated Bitwarden user, e.g. `kharon@<domain>`. That user is the only non-owner member of a dedicated Vaultwarden organization, `kharon`, created for this purpose. It has Can view access to that org's collection(s) and to nothing else. The owner adds new items to that org, or moves or clones existing personal items into it, through the web vault. kharon sees exactly the items in that org and its configured collections. Edits, additions, and removals made in the web vault reach kharon through periodic `/api/sync` (and the notifications hub when available), with no restart. A Bitwarden item has exactly one owner, so an item kept in both places is two copies. The owner keeps agent-usable credentials only in the kharon org (OQ-5, resolved).

Login uses the account's personal API key, `client_credentials` grant with `client_id=user.<uuid>` and `scope=api`. This authenticates to the server but does not decrypt. Decryption needs the master password. An organization API key cannot be used: it reaches the Public API only and yields no vault keys.

Key derivation chain, per the Bitwarden Security Whitepaper. Verify each line against the whitepaper and sdk-internal `bitwarden-crypto` during M1 (REQ-CRY-010).

| Step | Construction |
|---|---|
| KDF params | `POST /identity/accounts/prelogin` → `{kdf, kdfIterations, kdfMemory, kdfParallelism}` |
| Master key (32 B) | PBKDF2-HMAC-SHA256(password, salt=lowercase(email), iters; default 600 000), or Argon2id(password, salt=SHA-256(lowercase(email)), m=64 MiB, t=3, p=4 defaults) |
| Stretched master key (64 B) | HKDF-Expand-SHA256(masterKey, info="enc", 32) ‖ HKDF-Expand-SHA256(masterKey, info="mac", 32) |
| Server auth hash | PBKDF2-HMAC-SHA256(masterKey, salt=password, 1). Not needed for API-key login, but needed for password login and `/accounts/verify-password`. |
| User key (64 B: enc‖mac) | Token/sync response `Key`: EncString type 2 = AES-256-CBC + HMAC-SHA256 (encrypt-then-MAC over iv‖ct), under the stretched master key |
| RSA private key | `PrivateKey`: PKCS#8 RSA-2048, EncString type 2 under the user key |
| Org key (64 B) | `profile.organizations[].key`: EncString type 4 = RSA-2048-OAEP-SHA1 under the user's public key |
| Cipher key (optional, per item) | `cipher.key`: EncString type 2 under the org key. If present, fields are under it. Newer clients set it. |
| Fields | `login.username`, `login.password`, `login.totp`, `login.uris[].uri`, `name`, `notes`, `fields[]`: EncString type 2 |

Known uncertainty: Bitwarden is rolling out "account cryptography v2" (COSE-encoded keys, XChaCha20-Poly1305 EncString type 7, signing keys). Whether Vaultwarden serves v2 material, and when official cloud migrates existing accounts, is unverified (OQ-8). kharon must fail closed on unknown EncString types.

### 3.1a Export mode (optional, offline)

For air-gapped use, kharon can run with no Vaultwarden account. It loads a password-protected encrypted Bitwarden JSON export (`"encrypted": true, "passwordProtected": true`) at startup. In that format the export is under a key derived with the export's KDF params and a salt, and `encKeyValidation_DO_NOT_EDIT` checks the password. Verify the exact format against the official clients during implementation. Account-restricted encrypted exports are refused because they need the account's user key. Updating means replacing the file and restarting. There is no sync. All grant, origin, audit, and memory rules apply unchanged.

Risks:
- Plaintext JSON or CSV exports are never accepted. The broker refuses them at load.
- The export password must be held somewhere. It is supplied at unlock like the master password, never in config, env, or disk. An unattended restart therefore stays locked.
- The export file is a full offline-attackable copy of the items. Its strength is the export password and KDF. Item revocation requires replacing the file.
- Staleness: a rotated password in the real vault is not reflected until the file is replaced.

| ID | Requirement | AC |
|---|---|---|
| REQ-EXP-001 | `mode = "export"` loads a password-protected encrypted Bitwarden export. No network to any Bitwarden server. | Fixture produced by `bw export --format encrypted_json --password …` loads. `list` matches the source. Network namespace with no egress: works. |
| REQ-EXP-002 | Refuse plaintext JSON, CSV, and account-restricted exports. | Each fixture → startup error `ExportNotPasswordEncrypted`. No item parsed or logged. |
| REQ-EXP-003 | Export password supplied only at unlock (CLI/web), zeroized after key derivation. Boots locked. | Config/env keys for the password are rejected. Canary scan after unlock finds 0 hits. Restart → `locked`. |
| REQ-EXP-004 | No sync in export mode. Update = replace file + restart. File SHA-256 recorded in an audit `export_loaded` entry. | Changing the file without a restart does not change `list`. After restart, the audit has a new hash. |
| REQ-EXP-005 | Wrong password or a failed validation field → refuse without partial load. | A bad-password fixture → `ExportAuthFailed`, 0 items. |

### 3.2 Components

- `kharond`: broker daemon on owner hardware. It holds keys, enforces grants and origin binding, drives CDP, and writes audit. It exposes MCP (streamable HTTP) and an HTTP API to agents, and a separate owner API: unix socket for the CLI, plus web UI.
- `kharon` CLI: owner tool for unlock, lock, approve, revoke, and audit verify.
- Fill transport on the agent host: Chromium plus a tunnel endpoint.

### 3.3 How secrets reach the page

| | (a) Broker drives Chromium over CDP via tunnel | (b) Fill helper on agent host as separate OS user |
|---|---|---|
| Plaintext path | broker RAM → TLS/WG → Chromium browser process → renderer | broker → helper process (agent host) → CDP/native messaging → renderer |
| New agent-host process holding plaintext | None (Chromium already must) | Helper. Ptrace-protected only if `kernel.yama.ptrace_scope≥1` and the users differ. Its sockets/IPC are reachable by the agent user. |
| Agent-host secrets at rest | Tunnel client key only, which grants CDP to the browser the agent already controls | Helper credentials to the broker (a bearer that can request fills); config files root-owned |
| Attack surface reachable by the agent user | Chromium's CDP endpoint (already reachable) | Plus the helper IPC: parser bugs, confused deputy |
| Origin check runs | In broker, against the frame's live origin via CDP | In helper. Separation depends on host user isolation. |
| Install footprint | Chromium flag plus a tunnel. No kharon code on the agent host. | Package, service user, sudo/systemd setup |

(a) is the stronger boundary. Plaintext and all policy code stay on owner hardware. The only new thing on the agent host is a path into a browser the agent already drives, so it adds no agent-reachable component that holds secrets or credentials to the broker. (b) adds a local privileged peer whose isolation depends on the agent host's Unix permissions, which the threat model assumes are partly compromised. Both share the N1 limit.

Recommendation: (a). Chromium runs as OS user `browser` with `--remote-debugging-port` bound to 127.0.0.1, or `--remote-debugging-pipe` behind a small root-owned relay. The broker reaches CDP through one of two transport classes (both satisfy REQ-ARCH-002):

- **(A) WireGuard / mTLS stunnel / `ssh -R`** — broker dials the agent host. Preferred when the agent host can accept or peer a tunnel (UDP/WG or inbound TCP).
- **(B) Agent-initiated connector** — a non-secret-bearing tunnel client on the agent host dials the broker over outbound HTTPS/TLS (proxy-friendly); the broker's CDP client rides that reverse path to `127.0.0.1:9222`. Preferred when the agent host is egress-shaped (outbound TCP/TLS only, NAT/proxy, no UDP egress, no `CAP_NET_ADMIN`). This is the connector pattern used by systems kharon is modeled on.

The agent keeps its own CDP session (Playwright/puppeteer `connectOverCDP`). kharon opens a separate CDP session. Running as a separate user does not stop the agent attaching to CDP, because it does that already. It does stop the agent reading the profile dir and `/proc/<pid>/mem` (`ptrace_scope`).

## 4. Agent-facing API

Exposed as MCP (tools below) and HTTP `/v1/*`, with identical semantics. Auth: `Authorization: Bearer kh_agent_<id>_<random32>`. Only the Argon2id hash of the token is stored. One token per agent identity. The owner mints the token out of band with `kharon token mint <id>` (§7); the daemon does not. A dashboard instead connects with MCP OAuth and calls `POST /mcp` with a short-lived access token, `kh_at_…`, issued by the deploy's own authorization server (§4.1).

### 4.1 Connecting from a dashboard (MCP authorization, N3)

A customer connects a dashboard (an MCP client such as Muse's or Grok's) with a **Connect** button instead of pasting a `kh_agent_` token. This is the MCP 2026-07-28 authorization flow: OAuth 2.1, authorization code with PKCE. The design is `docs/superpowers/specs/2026-11-10-n3-mcp-oauth-connect-design.md` (#213, #226).

**Roles.** kharond plays both roles, on two hostnames:
- **The resource server** is `POST /mcp` on `[public_ingress]` (the agent hostname).
- **The authorization server** is on the owner hostname, where the owner's passkey lives (`[owner_ui]`, #208). The **issuer** is the owner origin with no path.

**Configuration.** `[oauth] clients` lists the Client ID Metadata Document URLs the deploy accepts. `[oauth]` requires `[public_ingress]` and a public `https` `[owner_ui]` origin.

**A Connect.**
1. The owner signs in with their passkey and approves a plain-words consent screen with a fresh passkey assertion.
2. kharond then issues a one-time code.
3. The dashboard redeems the code. That creates one **Connect identity**, `c-<10 base32>`: an agent identity that exists only at runtime, not in `kharon.toml`. The dashboard receives a token pair.
4. From then on, every fill is approved by the owner exactly as for any agent (§5). Consent creates a connection; it never creates or pre-approves a grant.

**Phase 1.** Dashboards get MCP calls and grant requests. Fills wait for phase 2 (#235), in which the dashboard runtime attaches a browser through the connector (#199).

## 6. Origin binding

The match is computed from the decrypted `login.uris[]` and their Bitwarden match type (`uri.match`, or the account default, `Domain`):

| BW match | kharon v1 |
|---|---|
| Domain (0) | eTLD+1 via the Public Suffix List (`publicsuffix` crate, PSL snapshot pinned and updated in release) equal |
| Host (1) | host and port equal |
| StartsWith (2) | Origin must also be Host-equal. Prefix check on full URL. |
| Exact (3) | full URL equal (origin + path) |
| RegularExpression (4) | Refused (`origin_mismatch`). Fail closed. |
| Never (5) | Refused |

Rules: scheme must be `https`, except `http://localhost`/IP only if the item URI is literally http and `allow_http=true`. The page must be a secure context. A grant request is not created for a claim that already fails this scheme rule: a claimed origin whose scheme is not `https` is refused before prompting (`origin_mismatch` / `insecure_context`), unless the claim is `http` and `allow_http=true` (#180). The claim alone decides this — no live observation is made — so whether an iframe target is allowlisted, which only the live check can know, still refuses there. Frame origin and top-level origin must both match (default). Config `allow_cross_origin_iframe_hosts` permits named IdP iframes. An allowlisted iframe is matched on its own origin: the top-level page need not match the item, since an identity provider's frame is embedded in a relying party's page (#180). A cross-site iframe whose host is not allowlisted is refused as `origin_mismatch` with `detail_code: iframe_not_allowlisted`, and it counts toward REQ-RL-002's mismatch streak like any other `origin_mismatch`. Origins in the IDN and punycode form are compared after `idna` normalization. A PSL private-section entry, such as `github.io`, makes the eTLD+1 the user's subdomain, which is intended.

Redirect-race defense. The check and the write happen in one renderer task:
1. `Page.createIsolatedWorld(frameId)` → contextId. Record `loaderId`.
2. `Runtime.callFunctionOn` in that context with args `(matchers, kind, selector, secret)`. Comparand per match type: Domain → `location.protocol` plus `location.hostname` equal to or ending in `.`+d, where the broker PSL-reduced d (no PSL in-page). Host → `location.origin`. Exact → `location.href` equal. StartsWith → `location.origin` equal and `location.href` prefix. The function checks these and `window.top.location.origin` if same-origin-accessible (else uses step 1's frame-tree origin check). It resolves the field, sets the value via the native `HTMLInputElement.prototype.value` setter, and dispatches `input` and `change`. All of this runs synchronously, so JS run-to-completion means no navigation can commit mid-function.
3. If the document navigates, the isolated world context is destroyed and the call fails (`navigated`). It cannot land in the new document.
4. After the call: check that `loaderId` is unchanged. If it changed and the call did not itself dispatch submit (`submit: false`, or a failure that returns before this check), attempt a clear in the old context (best effort) and report `navigated`. If the call reported success and itself dispatched submit (`submit: true`), a loader change is that submit's own navigation: report `filled` with `fields_filled` (REQ-API-008).

A fallback path, `Input.insertText` for sites that ignore programmatic value sets, would be gated by a pre-check plus a post-check of `loaderId` and origin. It is weaker: there is a race window between focus and insert. It is not implemented in v1 (OQ-9, #135).

Local-only checkpoints require `audit_checkpoint_local_only=true`, which is logged as a startup warning. Events: unlock, lock, list, search, fill_*, context_open, context, grant_request, grant_issue, grant_revoke, token_create/revoke, owner_auth_fail, rate_limit, panic, connector_auth_fail, connector_replaced, oauth_connect, oauth_disconnect, oauth_refresh_reuse, oauth_connector_grant, oauth_client_refused, passkey_enroll_code, passkey_enrolled, passkey_listed, passkey_removed.

Connector events (#199) are rate-bounded, because the WebSocket path is reachable from the internet and every entry grows the chain and the off-host checkpoint stream. `connector_auth_fail` is written when a hello credential is refused for a **configured** agent id or a Connect identity in the OAuth store, ended ones included, with `agent_id` (the claimed id), `transport` (`tls` or `ws`) and `detail_code`: `unauthorized` for every tunnel refusal and for a Connect token that is not live, otherwise `audience`, `identity` or `scope` (REQ-OAU-009). The detail codes share the event's window. The token is never in an entry or a log line. A malformed hello carries no attributable agent id, so it is not audited. `connector_replaced` is written when a new session evicts a live one for the same agent, with the new session's `transport` and the evicted session's age in `old_session_secs`. Each event is written at most once per (agent, event) per 60 s window. The two events keep separate windows, so a flapping connector can write both inside one minute. Further events in a window are counted, and `suppressed` reports the count on that agent's next entry of the **same** event. A count that no later event carries still reaches the log (#219). When a window has closed and still holds a count, a **summary entry** is written: the same event with only `agent_id`, `suppressed = N` and `result = "suppressed_only"`. It has no `transport`, `detail_code` or `old_session_secs`. The window is then dropped. Closed windows are checked every 15 s, so a count is written within 75 s of the burst's last event. At shutdown every window that still holds a count gets a summary, written before the exit checkpoint so the checkpoint anchors it. Unknown agent ids and junk are never audited: they appear only as counts in a once-a-minute log line, so a stranger cannot grow the log. An append failure is logged and never changes the auth result or the eviction.

OAuth events (N3, §4.1) reuse the entry's fields. `agent_id` is the Connect identity `c-…`. `origin` is the client's CIMD hostname. `channel` is `web_ui` or `cli` for an owner action. It is absent for events caused by the client's own requests: a redemption, a connector spawn, `/oauth/revoke`, a refresh reuse or a refused client. `detail_code` comes from an enum.

The events:
- `oauth_connect` is written when a code is redeemed. The owner's consent click alone writes nothing, because an unredeemed consent leaves nothing behind.
- `oauth_disconnect` covers Disconnect, `revoke agent`, `/oauth/revoke` with a refresh token, panic and code re-redemption. Its `detail_code` is one of `owner`, `client`, `panic`, `code_reuse` or `persist_failed`.
- `oauth_refresh_reuse` is written when a retired refresh token comes back outside the grace.
- `oauth_connector_grant` is written once when a connector family is spawned. `agent_id` is the `c-…` id, `origin` is the CIMD hostname, and there is no channel. `result` is `issued`. It carries no token and no pin. A lost-response retry of that spawn writes nothing. A failed persist rolls the new family back, leaves the MCP refresh token live, and appends a compensating entry with `result` and `detail_code` `persist_failed`.
- `oauth_client_refused` has no `agent_id`. Its `detail_code` is `not_allowlisted`, `cimd_unavailable`, `cimd_invalid` or `redirect_mismatch`.

Ordering follows REQ-AUD-003. A Connect appends `oauth_connect`, then persists the identity and its first token pair, then answers.
- A failed append fails the request, with no identity and no tokens.
- A failed persist after the append writes a compensating `oauth_disconnect` (`persist_failed`) on a best-effort basis and answers 500.
A connector spawn appends `oauth_connector_grant` with `result` `issued`, then persists the connector family, then answers. A failed append stores nothing. A failed persist writes the compensating `persist_failed` entry above and leaves the MCP refresh token live.

Revocations are revoke-first (#135): a Disconnect, a panic and a refresh reuse take effect before their entry is appended.

Token issue and refresh are not audited one by one, because they would grow the chain hourly per Connect. The connector spawn is the exception: one `oauth_connector_grant` per spawn, not per later refresh. Neither tokens nor codes ever appear in an entry.

Agent token provisioning is out of band (REQ-API-003, #129). `kharon token mint <id>` prints the token once and the Argon2id PHC string the operator stores as `[agents.<id>] token_hash`. The daemon never sees the plaintext and does not append `token_create` for that mint. `token_revoke` is still appended when `kharon revoke agent` runs (REQ-REV-001). `token_create` stays a recognized event name so a later in-daemon rotation can emit it; v1 does not. `sync` is likewise a recognized name that v1 does not emit (#135): a sync shows in the log through its effects, such as REQ-REV-003's `grant_revoke` entries.

Passkey enrollment (#249, REQ-APR-005) is two entries, written before the step they record, the way a fill's `fill_dispatch` is. A failed append fails the action (`audit_failed`). The enrollment code and the credential id never appear in an entry.

- `passkey_enroll_code` is written on channel `cli` with result `minted` when the owner socket mints an enrollment code, before the code exists. A failed append returns no code.
- `passkey_enrolled` is written on channel `web_ui` with result `enrolled` when a passkey is stored, before the store. It carries `credential_fingerprint` (the first 32 lowercase hex chars of SHA-256 over the raw credential id) and `passkey_count` (the enrolled-passkey count after the store). A failed append stores nothing.

Passkey list and remove (#258, REQ-APR-005, REQ-APR-006) are two more entries, written before the step they record. A failed append fails the action (`audit_failed`). The credential id and the public key never appear in an entry. The short id an owner types is the first 8 lowercase hex chars of `credential_fingerprint` and is not its own field.

- `passkey_listed` is written on channel `cli` (owner socket) or `web_ui` (signed-in page) with result `listed` when passkeys are listed, before the list is returned. It carries `credential_fingerprints` and `passkey_count`. A failed append returns no list.
- `passkey_removed` is written on channel `cli` or `web_ui` with result `removed` when a passkey is removed, before the store changes. It carries `credential_fingerprint` and `passkey_count` (the count after the removal). A failed append removes nothing and leaves sessions in place. The web UI refuses to remove the last passkey and writes no entry; the CLI allows it.

Revoke-first (#135): when a sync invalidates grants (REQ-REV-003), they are removed from memory before their `grant_revoke` entries are appended. If an append fails, the grant stays removed, because an audit failure must never undo a revocation; the failure is logged as an error so the gap in the log is explained. That is REQ-AUD-003's fail-closed rule applied to a restriction: the closed state is the grant removed, not restored.

## 8. Unlock and key lifecycle

- Start state is always `locked`. The master password is supplied only by the owner via CLI (tty, no echo) or web UI after WebAuthn. It is never stored on disk, in env, or in config.
- The web UI never sends the master password in the clear (#131): behind the WebAuthn session, the page encrypts it to a single-use ephemeral key the daemon issues for that one attempt (ECDH P-256, HKDF-SHA256, AES-256-GCM), so HTTP buffers only ever hold ciphertext. REQ-MEM-003's canary-scan AC covers a web unlock as it does a CLI one, and no owner-UI route accepts a `password` field.
- Unlock derives the master key, decrypts the user key, then zeroizes the master key and password immediately. In memory it keeps the user key, the RSA private key (zeroized once org keys are unwrapped), and the org key(s). Cipher fields are decrypted per fill into `Zeroizing` buffers and dropped after CDP write.
- The API key (`client_id`/`client_secret`) is in a file or Docker secret readable by kharond, which runs non-root (REQ-DEP-008). On its own it yields ciphertext only: another local user or process that reads it can authenticate as the kharon account and sync ciphertext and metadata, but cannot decrypt without the master password.
- Process hardening: `prctl(PR_SET_DUMPABLE,0)`, `setrlimit(RLIMIT_CORE,0)`, `mlockall(MCL_CURRENT|MCL_FUTURE)` (needs `CAP_IPC_LOCK`, or memlock ulimit), `secrecy` + `zeroize` crates, `panic = "abort"` in release builds, no swap or encrypted swap, seccomp profile. There is no dedicated key arena: `mlockall` covers every page, and `MADV_DONTDUMP` is not applied because a non-dumpable process is never dumped (OQ-10). The `kharon` CLI, which holds the master password and fresh tokens, also makes itself non-dumpable with core limit 0 (#134).
- Idle lock: `idle_lock = 30m` (configurable) since the latest of a fill, an owner unlock, or the owner approval that issues a grant (`grant_issue`). Agent-only traffic does not reset it: `kharon_context`, status, list, search, `grant_request`, and tab navigation. The broker never sees tab navigation, so moving between tabs cannot reset the timer. While an issued grant is still live (unconsumed and unexpired), the idle lock is deferred until that grant is consumed or expires under its existing TTL, and not past that point. An explicit owner lock and panic still lock immediately, and `max_unlocked = 12h` absolute is not deferred. Lock zeroizes keys and closes CDP sessions. After any re-unlock the previous browser context is dead: the agent calls `kharon_context` again and uses the new id.
- Restart, crash, or OOM → locked. Pending requests are dropped and audited on next start as `abandoned`.
- Re-sync every 5 min while unlocked, and on `/v1/fill` if revision is older than 5 min. Server-side key rotation, which changes the org key, forces lock.
